# Issue or Discussion?

The rule of thumb: **an issue has a definition of done. If nobody can say what "done" looks like, it is a discussion.**

| It is an **issue** when | It is a **discussion** when |
|---|---|
| It is a defect with steps to reproduce. | It is a question or a how-to. |
| It is a concrete change someone intends to make. | It is an idea without an owner or an agreed scope. |
| It is a PLIP, or a task of a PLIP. | It is a proposal that needs debate first. |
| It is a release task. | It is feedback, an opinion, a "would it be nice if". |

Moving an idea to a Discussion is an act of hospitality. It says: this deserves a conversation without the pressure of an open issue, and it is the place where someone can pick the idea up and own it. The issue tracker is where commitments live; Discussions is where ownership can emerge. Converting is one click on the issue and reversible, and a discussion that matures can spawn issues. The proposal says this in exactly these terms, so that nobody reads *convert* as *reject*.

**Where discussions live.** Repository-specific topics go to the Discussions of that repository. Each team switches them on when it wants them; the proposal recommends it for volto, aurora, Products.CMFPlone, plone.restapi and documentation, with the categories *Ideas* and *Q&A*. General, cross-project and user questions stay on community.plone.org, as they do today. The issue form's `config.yml` links to both, so a reporter sees the choice before writing.
