# Principles

1. **A label exists only where GitHub has no native feature for that fact.** If a type, a field, a close reason, a milestone or a board state can carry the information, it does.
2. **A label says one of three things:** a state that needs a human to act (`needs:`), the single alarm `blocker`, or a concern that cuts across all repositories and has a team behind it (`accessibility`, `i18n`, `documentation`). Graded priority is not a label; it lives in the Priority issue field, on issues only. A pull request is the result of an issue and carries no priority of its own.
3. **The repository is the area.** No area or component labels in the shared set. Teams add their own where they need them.
4. **Forms set the initial state.** In the common path a maintainer removes a label or clicks a native control. Adding a label is the exception.
5. **Plain names, no numeric prefixes.** The prefixes existed to sort a label widget that has been searchable for years, and the `24`/`25` collision shows what they cost.
6. **The shared set is small and arrives everywhere by itself.** Repositories add local labels freely; those are theirs, and the rollout never touches them.
7. **Everything is an invitation.** Using the shared set is optional. An issue without labels or type is a normal issue, exactly as before. Nothing that was acceptable yesterday becomes unacceptable.
